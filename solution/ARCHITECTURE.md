# Crew Ops Advisor — Solution Architecture

**Hackathon:** dCortex "Agentic Crew Ops Advisor"
**Status:** Deterministic engine + tool boundary implemented and verified
(41/41 answer-key checks, 107 tests — see [README.md](README.md)). The LLM
adapter is the only unbuilt piece (provider TBD); it plugs into
`crew_ops/tools.py` with no changes elsewhere.

---

## 1. The One Decision That Matters

The problem statement asks a single architectural question:

> *What should the language model do, what should deterministic code do, and how do you compose them into a system that is both conversational and correct?*

Our answer, stated as a hard rule the whole system enforces:

> **The LLM never computes a number. Deterministic code never interprets language.**
>
> - The LLM does three things only: **understand** the controller's question, **plan** which tools to call, and **narrate** the tool results back in plain language.
> - Every fact, hour, cost, legality verdict, and ranking is produced by a **deterministic Python engine** operating on the dataset — with a machine-generated reasoning trace.
> - The LLM's narration is **grounded**: it may only reference values present in the engine's structured output. Numbers in the answer are substituted from the trace, never re-generated by the model.

Why this boundary and not another:

| Alternative | Why we rejected it |
|---|---|
| **Stuff all JSON into the prompt, let the model answer** | Works for Tier 1, fails Tiers 2–3. Duty-hour arithmetic across rolling calendar windows is exactly what LLMs approximate wrong — fluently and confidently. An answer that is 1h20m wrong on RULE-DUTY-02 is a regulatory violation, not a rounding error. |
| **LLM writes SQL / code per question (text-to-SQL, code-interpreter)** | Better, but the legality logic (FDP sector reductions, calendar-day windows, reserve on-call semantics, deadhead repositioning) is subtle enough that freshly generated code will be wrong in unverifiable ways. Also slow and non-deterministic — the same question can get different answers on different runs. |
| **Pure rules engine with keyword/NLU front end** | Correct but brittle and not conversational. Fails the "natural language is the primary interface" mandate the moment a question is phrased unexpectedly. |
| **Ours: LLM tool-calling over a fixed deterministic engine** | The rules are written **once**, tested against the provided answer keys, and reused for every question. The LLM contributes what it is actually good at — language and planning — and nothing else. Same question → same answer, every time. |

## 3. Deterministic Engine (the source of truth)

### 3.1 World State

All 10 JSON files load once at startup into an in-memory, indexed object graph (dataset is ~150 crew / 147 flights — no database needed; SQLite would add setup cost without benefit at this size, and we say so in the scalability section).

Indexes built at load:
- `crew_by_id`, `flight_by_id`, `flights_by(date, dep_station)`, `flights_by_aircraft_rotation`
- `pairing_by_id`, `pairings_by_crew`, `pairings_by_aircraft`, `crew_of_flight` (derived: flight → pairing → complement)
- `duty_history_by_crew` (28-day daily grid — this is what makes rolling windows computable on any date)
- `reserves_by(base, date)`, `certs_by_crew`, `risk_by_crew`

**Copy-on-write overlays** implement what-if: a simulation clones nothing, it layers a `Disruption` delta (crew removed, flight delayed, station closed, cert invalidated) over the base snapshot. This gives us scenario independence for free (S2's sick call never leaks into S6's world) and makes chained disruptions (an optional enhancement) a stack of overlays.

### 3.2 Rules Engine

One pure function per rule, signature `check(world, crew_id, proposed_duty) -> Verdict`:

```
Verdict = { rule_id, pass: bool, computed: {…}, limit: {…}, margin, detail }
e.g. RULE-DUTY-02 →
  { rule_id: "RULE-DUTY-02", pass: false,
    computed: { window: "2026-09-09..09-15", duty_hours: 61.33 },
    limit:    { max: 60 },
    margin: -1.33,
    detail: "48.50h (Sep 9–14 history) + 12.83h (proposed duty Sep 15) = 61.33h > 60h — exceeds by 1h20m" }
```

Domain conventions are encoded exactly as `rules.json` and the dataset README define them — these are the correctness traps the dataset is engineered around:

- **Duty period** = report (first dep −60 min) → release (last arr +30 min).
- **FDP-01**: max FDP = 13h − 0.5h × (sectors − 2).
- **DUTY-02 / FLT-03**: **calendar-day** rolling windows (7 / 28 UTC dates, inclusive of duty date), summed from `daily_history` **plus the proposed duty** — not the pre-baked `duty_hours_7d` summary, which is only valid as-of the snapshot.
- **REST-04**: ≥12h from last release to next report.
- **Reserve semantics**: the **required report time** (after any deadhead positioning) must fall inside the on-call window; once activated, a reserve is line crew — the window no longer constrains later days. (This is precisely the `C-3305` teaching trap: legal for day 1 of P-2291 in isolation, breaches DUTY-02 on day 2 — a per-day check that forgets multi-day pairings gets this wrong.)
- **Deadhead (BASE-07)**: positioning uses the real schedule (DEL→BLR via DX402 odd dates / DX589 even dates), new report = arrival +15 min, cost = callout + positioning + delay-hours × `delay_cost_per_duty_hour`.

**`legality_check(crew, assignment)` always runs all 7 rules** and returns all 7 verdicts, pass or fail. The trace therefore shows not just *why* an option is illegal but *what was checked* on a legal one — which is what `rules_checked` in the expected Tier-3 output shape asks for.

### 3.3 Simulation Engine (Tier 2)

Input: a typed `Disruption` — the same event vocabulary as `scenarios.json` (`SICK_CREW`, `STATION_CLOSURE`, `DELAY`, `CERT_EXPIRY`, `MULTI_SICK`) so the provided answer keys directly test this layer.

Pipeline: **event → affected pairings → uncovered/affected flights (all remaining legs of the pairing, both days) → downstream cascade** (aircraft rotation knock-ons for delays; re-run rules on the rostered crew under the shifted times to detect induced FDP/rest breaches) **→ impact summary** (flights, pairings broken, passengers = Σ seats, rule risks).

Output matches the problem statement's Tier-2 shape (`uncrewed_flights`, `pairing_broken`, `downstream_risks`, `passengers_affected`) plus the trace.

### 3.4 Recommender (Tier 3)

Deliberately a **transparent enumerate-filter-rank**, not an optimizer (explicitly not required, and explainability is weighted higher):

1. **Enumerate candidates** for each uncovered role: reserves at base → day-off line crew at base → deadhead candidates from other bases → (last resort) delay or cancel.
2. **Filter** each through the full 7-rule legality check against the overlay world.
3. **Cost** each from `costs.json` (callout / day-off / deadhead + delay hours / cancellation / hotel).
4. **Rank** lexicographically: coverage (full pairing first) → legal → total cost → delay → reachability. Equal-cost options share a rank tier (the S6 answer key treats mirror assignments as equally correct).
5. For `MULTI_SICK`: resolve jointly — greedy assignment over the small candidate set with a conflict check so one reserve is not recommended twice. At this scale exhaustive pairing of options is cheap.

Every option carries `legal`, `rules_checked` (all 7 verdicts), `cost_inr` (itemized), `coverage`, `delay_hours`, and the reasoning trace.

### 3.5 Reasoning Trace (explainability as a data structure, not prose)

Every engine response includes a `trace`: an ordered list of steps `{step, source_file, inputs, computation, result}`. The trace is **generated by the code that did the computation** — it cannot drift from the answer. The LLM summarizes it; the UI shows it verbatim under "Show reasoning". A controller can challenge any line and see exactly which file and which numbers produced it. This is our answer to "no reasoning trail".

## 4. LLM Orchestration Layer

Single Claude agent with **~10 typed tools** (JSON-schema’d, thin wrappers over the engine):

| Tier | Tools |
|---|---|
| 1 | `lookup_crew`, `lookup_flights(date?, station?, aircraft?)`, `get_duty_clock(crew_id, as_of_date)`, `get_reserves(base?, date?)`, `get_certifications(expiring_within_days? \| crew_id?)`, `get_risk_signals` |
| 2 | `simulate_disruption(event)`, `check_assignment_legality(crew_id, pairing_id \| flights, start_date)`, `compute_rest_requirement(release_utc)` |
| 3 | `recommend_options(disruption, constraints?)`, `draft_notification(crew_id, assignment)` * |

\* `draft_notification` is the one place generation is the point — but its facts (report time, flights, pairing) are injected from the engine, the LLM only words the message.

**Responsibilities of the orchestrator prompt:**

1. **Entity resolution** — "Captain Nair", "C-1042", "the VT-DXE captain", "tomorrow" → canonical IDs and UTC dates (snapshot "now" = 2026-09-14T18:00Z is in the system prompt). Ambiguity → ask a clarifying question rather than guess.
2. **Planning** — decompose multi-part questions into tool sequences (e.g. Q32 two sick captains → one `recommend_options` call with a `MULTI_SICK` event, not two independent calls).
3. **Grounded narration** — compose the final answer *only* from returned tool JSON. System prompt forbids introducing numbers/IDs not present in results; a post-hoc **groundedness check** (deterministic) scans the drafted answer for crew IDs, flight numbers, hours, and ₹ amounts and verifies each appears in the tool results — violations are stripped or the answer is regenerated. This mechanically enforces "invented facts are treated as failures".
4. **Honest refusal** — if no tool maps to the question (out of dataset scope, missing data, ambiguous beyond repair), say so explicitly: *"I can't answer that reliably from the data I have, because …"*. The scoring rubric rewards this over guessing.

**Latency budget:** one model round-trip to plan + tool execution (pure Python, <50 ms) + one round-trip to narrate ≈ 3–8 s. Tier-1 single-tool questions can stream the narration immediately. Well inside the "usable on a live shift" bar.

## 5. Conversational UI

Minimal web chat (React + FastAPI, or Streamlit if time-pressed — both acceptable per the brief; the differentiator is the reasoning display, not the framework):

- **Answer** in prose (LLM narration).
- **Structured cards** for Tier-2 impact and Tier-3 ranked options (legality badge ✅/❌, itemized cost, coverage, rule chips).
- **"Show reasoning"** expander per answer rendering the engine trace — rule-by-rule arithmetic with source files.
- **Confidence strip**: "Computed deterministically from 4 sources · 7 rules checked" vs. an explicit uncertainty note when the answer involved interpretation.
- Multi-turn context: the orchestrator keeps conversation history, so "what about C-2210 instead?" resolves against the active disruption overlay.

## 6. Correctness Harness (how we know it's right)

The dataset ships its own ground truth — we make it our test suite:

- **Regression runner**: replay all 38 `questions.json` prompts end-to-end and all 6 `scenarios.json` events through the engine; diff against `expected_answer` / `answer_key`. Run continuously during the hackathon; the demo can show the scoreboard.
- Engine unit tests pin the engineered facts: C-2087 breaches DUTY-02 by exactly 1h20m; C-3310 covers P-2291 at ₹18,500; C-2210 deadhead totals ₹41,200; C-3305 fails day 2; C-2091 fails QUAL-05.
- Because held-out scenarios reuse the same event types, passing the visible keys via a **general engine** (not answer-key lookup) is our generalisation story.

## 7. Known Limits & Failure Modes (to be reported honestly)

1. **Entity resolution is the soft spot.** The LLM can mis-resolve "the captain on that Delhi flight" to the wrong ID. Mitigation: resolved entities are echoed back in the answer ("Assuming you mean Captain A. Nair, C-1042…") so the controller can catch it; ambiguity triggers a clarifying question. This is our documented failure case candidate.
2. **Questions outside the tool vocabulary** (e.g. free-form optimization goals, "minimize crew fatigue this week") get an honest refusal, not an attempt.
3. **Recommender is heuristic**, not optimal: for joint multi-sick scenarios we rank greedily; a true optimum could differ under adversarial cost structures. At this dataset scale we can exhaust; at real scale we'd say so.
4. **Q38-style advisory questions** ("what should a morning briefing surface?") are opinion, not computation — the LLM answers with clearly-labeled judgement grounded in available fields, no fake precision.

## 8. Scalability & Production Notes (commentary, not build scope)

- **Scale**: at real-airline scale (10⁴ crew, 10³ daily legs) the in-memory world state moves to Postgres + an incremental legality cache keyed by (crew, date); the rules engine and trace format are unchanged — the boundary is the durable design, not the storage. Candidate enumeration gets pruned by base/rating indexes before rule-checking, and the recommender graduates to a CP/MIP solver behind the same tool interface.
- **PII**: crew names/reachability are personal data in production — engine-side role-based redaction (the LLM sees crew IDs, never phone-level data), audit-logged tool calls (the trace doubles as an audit record), and data residency with the airline. The LLM boundary helps here: sensitive fields simply never enter the prompt.
